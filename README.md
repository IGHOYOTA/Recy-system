# Recy registry

A Python 3.9+ project that scrapes Return-It Encorp's public registered-products
registry, reconciles a Supabase PostgreSQL mirror, and exposes a UPC verification
API on Render Free. GitHub Actions runs resumable scheduled scrapes. SQLite
remains available for local development.

## Deploy with Supabase, Render Free, and GitHub Actions

The repository includes deployment configuration. No cloud resources or secrets
have been created. Follow these steps after pushing the repository to GitHub.

### 1. Initialize Supabase PostgreSQL

Create a Supabase project, open **Connect → Session pooler**, and copy its exact
PostgreSQL connection string. Session pooling supports IPv4 connections from
Render and GitHub-hosted runners. Use `sslmode=require`; percent-encode reserved
password characters. This is a database credential, not an anon/service API key.
See [Supabase connections](https://supabase.com/docs/guides/database/connecting-to-postgres).

```sh
python3 -m venv .venv
source .venv/bin/activate
pip install .
```

Copy `.env.example` to `.env` and replace the placeholders. The file is ignored
by Git and is not loaded automatically. Quote values appropriately for your
shell, especially passwords containing `$`.

```sh
set -a
source .env
set +a
python -m recy init-db
python -m recy probe
```

`init-db` applies the packaged idempotent migration. Tables and the UPC function
live in the private **`recy` schema**, outside Supabase's default public Data API.
Keep this schema out of Supabase's exposed schemas. Product rows appear in
`recy.registered_products` after the first complete publication. The API never
runs migrations or creates tables on startup. Existing SQLite data is not
automatically copied; the first PostgreSQL scrape populates Supabase independently.

### 2. Deploy the API on Render Free

In Render, select **New → Blueprint**, connect this repository, and use
`render.yaml`. It defines one Free Python service:

| Setting | Value |
| --- | --- |
| Build | `pip install .` |
| Start | Gunicorn serving `recy.wsgi:application` on `0.0.0.0:$PORT` |
| Health check | `/health` |
| `DATABASE_URL` | Supabase Session pooler string; enter when prompted |
| `RECY_REQUIRE_POSTGRES` | `1`; disables accidental SQLite fallback |
| `RECY_API_KEY` | Secret automatically generated by Render |

Retrieve `RECY_API_KEY` from Render's environment settings for your calling
application's server-side secrets. API routes require this Bearer token. Keep it
out of public browser code; access this API through your authenticated backend.
Render Free sleeps after 15 idle minutes and takes about a minute to wake.
Data lives in Supabase because Render's local filesystem is ephemeral. No paid
Render worker or cron job is configured. See [Render Free limits](https://render.com/docs/free).

```sh
curl https://YOUR-SERVICE.onrender.com/health
curl https://YOUR-SERVICE.onrender.com/ready
curl -H "Authorization: Bearer $RECY_API_KEY" \
  https://YOUR-SERVICE.onrender.com/api/v1/upcs/080696922510
```

`/health` is process health and does not contact the database. `/ready` verifies
database access and a published registry; 503 before the first complete scrape
is expected. Neither health endpoint requires authentication. API routes return
401 for missing/wrong tokens and 503 when the database is unavailable.

### 3. Enable GitHub Actions scraping

In **Settings → Secrets and variables → Actions**, add a repository secret
named **`DATABASE_URL`** with the same Supabase Session pooler string. Then open
**Actions → Refresh Return-It registry → Run workflow** for the initial scrape.

`.github/workflows/scrape.yml` installs the project, applies the migration, and
checks daily at **03:23 UTC**. A completed registry is refreshed every **7 days**.
Each invocation works for at most **3 hours**, checkpointing fetched pages in
Supabase. An unfinished scrape continues on the next daily or manual run. Daily
checks exit quickly when a completed registry is less than seven days old.
The overall job timeout is 200 minutes. Workflow concurrency prevents overlapping
scheduled/manual runs. No credentials are saved in workflow files or artifacts.

The active product table changes only after every page passes validation. An
interruption can lose the currently fetched page, but committed checkpoints
survive. When the source update date, count, first-page columns, or first-page
rows change, the old checkpoint is discarded. Fetched pages must match the
source update date/count; the first page is checked again before publication.
The source has no transactional snapshot feed, so changes elsewhere that do not
alter these indicators cannot be ruled out.

Checkpoints contain table content and relevant links, excluding repeated site
navigation and scripts. They are deleted after successful publication. Monitor
Supabase storage and GitHub Actions usage: public standard runners are free,
while private repositories have a finite monthly allowance. Frequent restarts
or long scrapes can exhaust it. Schedules can be delayed.
See [Actions billing](https://docs.github.com/en/actions/concepts/billing-and-usage).

Run the same scheduled operation locally after loading environment variables:

```sh
python -m recy scheduled-sync --interval-days 7 --max-seconds 10800
```

Use `--interval-days 0` to force a refresh. `--dry-run` retains checkpoints and
checks the final reconciliation without publishing. An incomplete successful
run reports `status: checkpointed`; a publication reports `status: published`.

For local production-server testing:

```sh
gunicorn recy.wsgi:application --bind 127.0.0.1:8000
```

## Run

From this project directory:

```sh
python3 -m recy probe
python3 -m recy sync --dry-run
python3 -m recy sync
python3 -m recy serve
```

The API listens on `http://127.0.0.1:8000`. Use another terminal:

```sh
curl http://127.0.0.1:8000/api/v1/upcs/001234567890
python3 -m recy verify 001234567890
python3 -m recy status
```

`001234567890` is an example identifier, not a verified registered product.
Without `DATABASE_URL`, the local database defaults to `data/registry.sqlite3`; override it with
`RECY_DB` or `python3 -m recy --db /path/registry.sqlite3 ...`.
`DATABASE_URL` selects PostgreSQL and takes precedence over the local path.

`probe` fetches only the first, second, and last pages and reports their schema,
row ranges, and advertised total. It does not open or change the database.
A full sync fetches all 5,213 pages at the observed registry size. Allow several
hours, depending on response time. `sync --dry-run` also fetches every page;
use `probe` for a quick connectivity check.

## Schema contract

`registered_products` is created only after a complete scrape is validated.
Its columns exactly match the **public HTML result table's header labels and
order**, with no added ID, timestamps, or sync columns. All values are stored
as TEXT, retaining displayed text and leading zeroes; HTML entities are decoded
and display whitespace collapsed. Missing UPC cells remain empty strings.
Return-It's private database schema, SQL types, keys, and unpublished fields
cannot be determined from its website, so this project does not claim to mirror
that private schema. Public header parity has been verified on sampled live pages.

Operational metadata lives in the separate `sync_runs` table. The UPC expression
index belongs to `registered_products` and adds no columns. Matching removes
spaces and hyphens, but never strips leading zeroes or converts codes to numbers.
All rows matching a code are returned; UPCs are not assumed unique.
UPC-A/EAN/GTIN equivalence and check-digit validation are not applied.

## Synchronization

The scraper fetches the unfiltered search and discovers numbered pagination
links on each response. It follows the site's link URLs and pagination parameter
names rather than assuming a specific page parameter. The five empty search
fields are retained on every request. Page numbers must cover every page from
1 through the last discovered page. A result count, when present, must match
the number of collected rows. Without a count, multiple numbered pages and
consistent page sizes are required, with a possibly shorter final page.
Repeated rows across different pages are rejected to detect ignored pagination
parameters or a changing source.
Products without UPCs are retained to preserve the source table.

Only after every result page succeeds does one transaction add new rows and
delete rows absent from the snapshot. An edited product row counts as a removal
and an addition because no stable source ID is known. A failed request, count
mismatch, unknown schema, pagination loop, or empty snapshot leaves existing
product records unchanged. A source header change requires an explicit migration.
A snapshot started before the latest committed sync is rejected.

By default, a sync that would remove more than 25% of existing rows is rejected.
After checking a large legitimate source change, adjust this limit explicitly:

```sh
python3 -m recy sync --dry-run --max-removal-fraction 0.5
python3 -m recy sync --max-removal-fraction 0.5
```

Use `--count-pattern 'YOUR_REGEX_WITH_COUNT_CAPTURE_GROUP'` once the source's
actual total-count text is known. A single page without a result count cannot
establish completeness and is rejected. Requests
are sequential with at least one second between them (`--delay` changes this).
No automatic retry loop repeatedly hits blocked requests.

PostgreSQL loads incoming rows using COPY and replaces active rows in one
transaction; readers see either the previous or the new complete registry.
An advisory lock serializes publications. PostgreSQL's removal guard compares
distinct product content excluding the `#` display position, because source
insertions can renumber many existing rows. The `#` column is still mirrored;
whole-row addition/removal reports include renumbering changes. Resumable
`scheduled-sync` requires PostgreSQL; the plain `sync` command is uninterrupted.

## API

| Method | Path | Behavior |
| --- | --- | --- |
| GET | `/api/v1/upcs/{upc}` | 200 with `registered`, `matches`, `last_synced_at`, and `source_url` |
| GET | `/api/v1/schema` | Exact imported column labels and their local storage type |
| GET | `/health` | Process health |
| GET | `/ready` | 200 after first committed sync; 503 beforehand |

Before the first sync, lookup and schema endpoints return 503 rather than
reporting a code as unregistered. Malformed codes return 400; an unknown code
returns 200 with `registered: false`. An absent code means **not found in the
local snapshot**. Return-It notes that not all registered products have a UPC
documented. Every lookup includes the last sync time so callers can assess age;
readiness does not imply freshness. API lookups never request the upstream site.

The `serve` command remains an unauthenticated development server. Hosted traffic
uses Gunicorn and `recy.wsgi:application` with Bearer authentication, as configured
in the Render Blueprint. There are no public write routes.

## Tests

```sh
python3 -m unittest discover -v
```

Tests cover synthetic HTML parsing, pagination, completeness rejection, exact
column preservation, leading zeroes, additions/removals, dry runs, rollback on
failure, schema drift, stale concurrent snapshots, and actual local HTTP lookups.
Captured live tables exercise the real column headers, title-attribute total,
pagination links, disabled Next link, and first/second/last-page probe. The tests
run offline; `python3 -m recy probe` performs the separate live connectivity check.

Deployment tests also cover Bearer authentication, missing PostgreSQL configuration,
source-generation changes, and interruption/resume without partial publication.
PostgreSQL tests require `TEST_DATABASE_URL` pointing at a disposable database
named **`recy_test`**; they reset its `recy` schema. Never use your Supabase
production URL. `.github/workflows/test.yml` provides an isolated PostgreSQL 17
service and runs the full suite on pushes and pull requests.
